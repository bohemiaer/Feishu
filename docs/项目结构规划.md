# 项目结构规划

## 1. 现状判断

当前仓库已经具备 MVP 可运行能力，但整体更像“原型脚本集合 + 样例数据仓 + 领域模块雏形”的混合体。

目前的优点：

- `src/agents`、`src/llm`、`src/preprocess` 已经有明确职责边界。
- `schemas` 独立存在，说明你已经在做结构化输出约束。
- `scripts` 基本承担了流程入口角色，便于快速演示。
- `case_sources`、`samples`、`demo_outputs` 等目录把“输入样本”和“输出结果”保留了下来，适合比赛和 MVP 验证。

目前的主要问题：

- 顶层目录同时混放产品文档、架构图、样例数据、运行输出、脚本入口，后续扩展会越来越乱。
- `scripts` 里既有纯 CLI 入口，也有较重的业务编排和飞书同步逻辑，维护成本会逐步上升。
- `src` 目前按技术职责拆分是对的，但还缺少“工作流层”和“集成层”。
- 数据目录命名偏场景化，后续一旦 case 增多，`case_sources`、`samples`、`demo_outputs`、`evaluation_inputs` 会变得不好管理。

一句话判断：

这个仓库现在最适合从“比赛型 Demo 仓库”演进成“可持续迭代的 Agent Workflow 仓库”，而不是直接重构成重量级单体服务。

## 2. 目标结构

建议目标结构如下：

```text
.
├─ docs/
│  ├─ product/
│  ├─ architecture/
│  ├─ prompts/
│  └─ decisions/
├─ data/
│  ├─ cases/
│  │  ├─ raw/
│  │  └─ generated/
│  ├─ fixtures/
│  ├─ outputs/
│  └─ seeds/
├─ schemas/
├─ scripts/
│  ├─ dev/
│  ├─ demo/
│  └─ sync/
├─ src/
│  ├─ agents/
│  ├─ workflows/
│  ├─ preprocess/
│  ├─ integrations/
│  ├─ domain/
│  ├─ llm/
│  ├─ shared/
│  └─ config/
├─ tests/
│  ├─ unit/
│  ├─ integration/
│  └─ fixtures/
├─ package.json
└─ README.md
```

## 3. 各层职责

### `docs/`

只放文档，不放运行数据。

建议继续细分：

- `docs/product/`：PRD、比赛要求、评估维度说明。
- `docs/architecture/`：系统架构、流程图、数据流说明。
- `docs/prompts/`：Agent system prompt、提示词模板。
- `docs/decisions/`：关键设计决策，记录为什么这么拆。

### `data/`

把“样例输入、生成数据、演示输出、初始化数据”统一收口。

建议划分：

- `data/cases/raw/`：原始 case 来源，替代现在的 `case_sources`。
- `data/cases/generated/`：由脚本生成的结构化中间产物。
- `data/fixtures/`：测试或脚本运行需要的小型固定样本。
- `data/outputs/`：演示结果、pipeline 输出，替代 `demo_outputs`。
- `data/seeds/`：飞书 base 初始化数据、模板数据，替代 `feishu_seed`。

这样做的好处是，所有“非代码资产”都能快速定位到 `data/`。

### `schemas/`

这一层保留独立目录是合理的，建议继续维持。

后续可以再细分为：

- `schemas/input/`
- `schemas/request/`
- `schemas/result/`

如果当前文件数不多，也可以先不拆。

### `scripts/`

这里建议只保留“薄入口”，不要继续承载复杂业务逻辑。

推荐规则：

- `scripts/demo/`：跑 demo 或 case 的命令入口。
- `scripts/sync/`：同步飞书、多维表、文档的命令入口。
- `scripts/dev/`：本地辅助脚本，例如清理输出、生成样例、校验 schema。

脚本文件内部只做三件事：

1. 解析参数
2. 调用 `src/workflows/*`
3. 打印结果或写文件

### `src/workflows/`

这是当前仓库最缺的一层。

它专门承载“多步骤编排”，把现在散落在脚本里的主流程收回到源码里。

建议包含：

- `src/workflows/demo_pipeline.js`
- `src/workflows/evidence_pipeline.js`
- `src/workflows/feishu_sync.js`

例如：

- `run_demo_pipeline.js` 应该只保留 CLI 壳，核心流程迁到 `src/workflows/demo_pipeline.js`
- `sync_demo_to_feishu.js` 的主体逻辑应迁到 `src/workflows/feishu_sync.js`

### `src/agents/`

这里保留“单个 Agent 能力模块”，现在的方向是对的。

建议约束为：

- 每个文件只负责一个 agent 的 request builder + model call + result normalize
- 不直接写文件
- 不直接依赖 CLI 参数
- 不直接操作飞书

### `src/preprocess/`

保留会议、文档、case 的结构化处理逻辑。

如果后续继续扩展，建议再拆成：

- `src/preprocess/parsers/`
- `src/preprocess/normalizers/`
- `src/preprocess/builders/`

当前规模下可以先不动。

### `src/integrations/`

这一层用来隔离外部系统接入，是另一个值得尽快补上的目录。

建议包含：

- `src/integrations/feishu/`
- `src/integrations/filesystem/`

飞书 CLI 调用、Base 写入、文档创建等，都应该逐步从脚本中迁进来。

这样后面如果从 CLI 切到 API SDK，改动会集中很多。

### `src/domain/`

这一层用来沉淀业务概念，而不是技术工具。

建议按业务对象拆：

- `src/domain/project/`
- `src/domain/meeting/`
- `src/domain/evaluation/`
- `src/domain/report/`

这里可以放：

- 字段映射
- 领域常量
- 状态机
- 指标计算
- 结果组装

你现在的 `src/protocol/execution.js` 更接近这个方向，后续可以并入 `domain` 或升级成 `shared/constants + domain/task`。

### `src/shared/`

放通用但不属于某个业务域的能力：

- 文件读写工具
- JSON 工具
- 参数解析
- 日志
- 时间处理

### `src/config/`

集中放配置加载逻辑。

建议把 `src/llm/config.js` 未来迁到这里，避免“配置只属于 llm”的误导。

可进一步拆：

- `src/config/llm.js`
- `src/config/runtime.js`
- `src/config/feishu.js`

### `tests/`

如果后续要持续演进，这层建议尽早建空目录。

优先级建议：

- `tests/unit/`：纯函数、parser、normalizer、metrics
- `tests/integration/`：workflow 级联测试
- `tests/fixtures/`：测试输入样本

## 5. 推荐重构顺序

不建议一次性大搬家，建议按下面顺序渐进处理。

### 第一阶段：先整理顶层目录

目标：让仓库“一眼能看懂”。

建议动作：

1. 新建 `docs/` 和 `data/`
2. 把产品文档、架构图、prompt 文档迁入 `docs/`
3. 把 `demo_outputs`、`case_sources`、`samples` 等迁入 `data/`
4. 更新 `package.json` 里的脚本路径

这一阶段收益最大，风险最小。

### 第二阶段：抽出 workflow 层

目标：把复杂流程从脚本里拿出来。

建议动作：

1. 新建 `src/workflows/`
2. 将 `run_demo_pipeline.js` 的核心逻辑迁入 `src/workflows/demo_pipeline.js`
3. 将 `sync_demo_to_feishu.js` 的核心逻辑迁入 `src/workflows/feishu_sync.js`
4. `scripts/` 只保留 CLI 参数和调用入口

这一阶段完成后，代码可测试性会明显提升。

### 第三阶段：补 integrations 和 shared

目标：降低耦合。

建议动作：

1. 把飞书 CLI 调用封装到 `src/integrations/feishu/`
2. 把重复的 `readJson`、`ensureDir`、`writeJson` 收敛到 `src/shared/`
3. 把配置读取统一到 `src/config/`

### 第四阶段：再考虑 domain 细化和测试

目标：把 MVP 变成长期可维护项目。

建议动作：

1. 抽领域对象和指标计算
2. 给 parser、normalizer、workflow 增加测试
3. 再视情况决定是否引入 TypeScript

## 6. 命名与边界约束

建议从现在开始统一下面几个规则：

- `scripts/` 只放入口，不放核心业务。
- `src/workflows/` 负责串流程，不直接关心终端输出格式。
- `src/agents/` 只负责单 Agent 行为，不负责外部系统同步。
- `src/integrations/` 只负责对接外部系统，不夹带业务判断。
- `data/outputs/` 视为可再生目录，尽量不要放必须手改的文件。
- `docs/` 视为说明性资产，不参与运行时依赖。

## 7. 对你这个项目最实用的结论

如果只选三个最值得马上做的动作，我建议是：

1. 先建立 `docs/` 和 `data/`，把顶层整理干净。
2. 新增 `src/workflows/`，把 `run_demo_pipeline.js` 和 `sync_demo_to_feishu.js` 的主体逻辑迁进去。
3. 新增 `src/integrations/feishu/`，把飞书 CLI 相关调用单独隔离。

这样不会破坏你当前 MVP 的演示能力，但会立刻让仓库更像一个可扩展项目，而不是一次性比赛交付物。
