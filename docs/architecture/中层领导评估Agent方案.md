# 中层领导评估 Agent 方案

## 1. 项目定位

**Manager Insight OS / 管理效能洞察系统**

它的目标不是简单评价某个中层“好不好”，而是基于飞书里的真实协作数据，持续判断一个中层管理者在项目推进中的以下能力：

- 是否能提出被项目后续结果验证的有效方向
- 是否能把会议结论转化为 owner、DDL、行动项和持续闭环
- 是否能提前识别关键风险，并推动可执行的缓释动作
- 是否存在废话过多、重复同步、辱骂羞辱、甩锅、情绪化施压等组织行为风险
- 是否体现出 AI 难以替代的人类管理增值，例如判断、取舍、协调、担责和组织影响力

这样包装有三个好处：

- 更符合企业真实需求，避免“AI 给领导打分”过于敏感
- 更容易解释评估依据来自哪里，减少主观性
- 更贴合比赛要求，因为它天然需要多个 Agent、持续流程、数据沉淀和报告输出

## 2. 当前收缩后的作品形态

当前版本先聚焦一个最容易跑通、最适合比赛演示的 MVP 场景：

- 场景：产品/研发项目周会
- 评估对象：项目型中层负责人
- 数据源：会议纪要/妙记、Base 项目/任务/风险、项目主文档/周报/复盘
- review 范围：只拉同项目下最近 3 到 5 场会议做复核 
- 核心评估维度：方向有效性、推进闭环力、风险识别力、组织行为健康度
- 辅助校正维度：事实依据力
- 观察项：项目熟悉度（保留观察，不作为核心淘汰指标）

建议你把系统设计成一个围绕“项目型中层管理者”持续运行的虚拟员工组织，而不是一个单次问答机器人。

核心业务链路：

**项目周会结束 -> 纪要/妙记进入系统 -> Data Collector 结构化事实 -> Evaluation Planner 决定本次评估重点 -> Agent 做方向/闭环/review、风险/行为审计 -> 人工复核争议或敏感结论 -> 输出评估报告和风险提醒 -> 结果回写 Base 和飞书文档 -> 进入下一周观察**

这正好满足比赛要求中的：

- 多角色 Agent 协作
- 基于多维表格建业务系统
- 通过 OpenAPI 持续读写数据
- 最终输出分析报告和决策建议

## 3. 飞书能力与可用数据源

你的原始想法从“会议记录”切入是对的，但如果只看会议，会很容易失真。更完整的评估应该做成“会议认知 + 任务闭环 + 文档依据 + 协同结果”的组合判断。

当前 MVP 只接入以下三类数据：

1. 飞书会议 / 妙记

- 会议主题、时间、参会人、发言纪要、重点讨论内容、行动项
- 可用于判断：该中层提出了哪些方向、是否形成闭环动作、是否识别到真实风险、会议行为是否健康

1. 多维表格 Base

- 项目主表、任务表、风险表、评估结果表
- 可用于判断：会议中的方向是否进入任务系统，后续是否闭环，风险是否升级或缓释

1. 飞书文档 / 云文档

- 项目主文档、周报、复盘
- 可用于校验：方向是否与项目目标一致，风险判断是否有依据，最终结果是否验证了会议中的管理判断

在当前假设中，项目资料整理较好，因此会议与项目、项目与主文档之间的映射默认可由结构化字段或命名规则直接建立。

当前版本先不引入：

- 全公司跨项目会议 review
- 私聊消息
- 审批、OKR、人事等高敏感数据
- 复杂组织协同网络分析

## 4. 最佳方案主题

### 方案名

**“管中台”Agent：基于飞书协作数据的中层管理效能评估系统**

### 一句话介绍

系统通过飞书会议纪要、Base 项目/任务/风险数据和项目主文档，构建一个持续运行的“数字督导组织”，对产品/研发项目周会中的项目型中层负责人进行动态评估，并自动生成管理洞察报告。

### 产品表现形式

产品不做独立 App，也不做单纯聊天机器人，而是嵌在飞书里的“管理效能评估工作台 + Agent 自动化流程”。

主要由四部分组成：

1. **飞书 Base 工作台**

- 项目、会议、评估任务、证据链、人工复核项、报告状态都沉淀在 Base
- HRBP、PMO、上级管理者可以在同一个工作台里看状态、看证据、看报告

1. **飞书机器人**

- 用于周会结束提醒、评估任务触发、人工复核通知和报告生成通知
- 遇到证据冲突、高风险语言、AI 替代风险偏高时，提醒人工介入

1. **飞书云文档报告**

- 用于输出正式成果
- 可生成 HRBP 版、PMO 版、上级摘要版和中层自查版

1. **人工复核台**

- 通过 Base 视图承载待确认事项
- 支持对 Agent 结论进行确认、驳回、降级、补充说明

因此系统不是“用户问一句、Agent 答一句”，而是持续运行的业务系统：

**会议产生数据 -> Base 状态更新 -> Agent 动态规划与分析 -> 人工复核介入 -> 报告生成 -> 结果回写 -> 下一轮跟踪**

## 5. Agent 员工组织设计

建议当前 MVP 固定为 `1 个脚本节点 + 4 个 LLM Agent`。这版保留同项目 review 机制，但把能力相近的角色合并，避免链路过长、职责重叠。

推荐原则：

- 稳定、重复、确定的工作交给脚本和工具
- 需要理解、判断、归因、解释的工作交给 LLM Agent

因此当前系统最合理的实现是：

- `Data Collector`：脚本化节点
- `Evaluation Planner`：规划节点，规则 + 轻量 LLM，不作为独立员工 Agent 展示
- `Management Reviewer`：LLM Agent
- `Risk & Behavior Auditor`：LLM Agent
- `Capability Assessor`：LLM Agent
- `Report Writer`：LLM Agent

### 节点 1：数据采集员 Data Collector

功能描述：

- 接收一次评估任务，并定位本次评估所需的原始材料
- 读取当前会议妙记、项目主文档、周报、复盘，以及同项目历史会议材料
- 将非结构化文本解析为结构化事实，供后续 LLM Agent 直接消费
- 完成字段标准化、时间格式统一、角色识别、发言拆分、行动项抽取和历史材料打包
- 只负责“拉数、清洗、组织事实”，不负责事实判断、能力打分和报告生成

实现方式建议：

- 优先脚本化实现
- 只在必要时调用抽取工具
- 不承担自由推理和高层判断

输入：

- 任务触发参数：`meeting_id`、`project_id`、`manager_id`
- 当前会议原始材料：会议妙记/纪要全文
- 项目材料：项目主文档、周报、阶段复盘
- review 材料：同项目最近 3 到 5 场会议妙记及其补充上下文
- Base 当前状态：项目、任务、风险的结构化记录

输出：

- `raw_payload`
  - 当前会议、项目、任务、风险、文档的统一结构化载荷
- `history_bundle`
  - review 所需的历史会议、历史任务变化、历史风险变化材料
- `meeting_fact_pack`
  - 面向后续 Agent 的标准事实包，包含：
    - 会议元数据
    - 管理者关键发言
    - 决策点
    - 风险点
    - 行动项
    - 文档摘要与引用锚点
- 可选回写结果
  - 输入索引、原始文本快照、结构化中间产物，写入 Base 观测表用于调试和复盘

### 节点 2：评估规划节点 Evaluation Planner

功能描述：

- 根据当前会议内容、项目状态、风险变化和历史反馈，决定本次评估重点
- 判断本次应走轻量周报、全量评估、专项风险审计，还是组织行为复核
- 生成后续 Agent 的执行计划和人工复核规则
- 它是流程规划节点，不作为独立员工 Agent 对外展示

输入：

- `meeting_fact_pack`
- 项目当前状态
- 风险等级变化
- 历史评估结果
- 上一次人工反馈

输出：

- `evaluation_focus`
- `execution_plan`
- `review_requirements`
- `human_review_rules`

### Agent 1：管理复核员 Management Reviewer

职责：

- 提炼中层在会议中给出的关键方向、判断、要求和决策口径
- 将这些方向与后续任务流转、周报、复盘、项目最终形态进行比对
- 评估方向是否被采纳、完成、废止或回滚
- 判断会议结论是否沉淀为 owner、DDL 和后续动作
- 调取同项目最近 3 到 5 场会议做 review，识别方向稳定性、闭环连续性和前后矛盾

输入：

- `meeting_fact_pack`
- `history_bundle`
- `execution_plan`
- 项目主文档、周报、复盘
- 任务状态与里程碑变化
- 同项目最近 3 到 5 场历史会议妙记

输出：

- 方向清单
- 方向采纳率
- 方向完成率
- 方向废止率
- 方向回滚率
- 方向有效性结论
- 行动项清单
- 行动项闭环率
- 延期事项恢复率
- review 复核结论
- 推进闭环力结论

### Agent 2：风险与行为审计员 Risk & Behavior Auditor

职责：

- 识别中层是否较早发现关键风险
- 判断其风险判断是否与项目实际演化一致
- 评估其是否给出了可执行的缓释动作
- 审计会议中的组织行为健康度，而不是只看项目事实
- 检测废话、重复同步、无效冗长表达
- 检测辱骂、羞辱、打断、甩锅、情绪化施压等负向管理行为

输入：

- `meeting_fact_pack`
- `history_bundle`
- `execution_plan`
- 风险表
- 周报、复盘中的风险记录
- 当前会议妙记全文
- 同项目历史会议妙记

输出：

- 风险命中清单
- 风险提前识别率
- 高等级风险命中率
- 缓释动作落地率
- 风险识别力结论
- 冗余发言占比
- 有效决策发言占比
- 负向行为事件清单
- 高风险语言标签
- 组织行为健康度结论

### Agent 3：能力评估员 Capability Assessor

职责：

- 汇总前置 Agent 的判断结果，形成最终画像
- 区分“正常项目波动”“需要辅导的问题”“高风险管理行为”
- 输出管理风险等级和 AI 替代风险指数

输入：

- Management Reviewer 结果
- Risk & Behavior Auditor 结果
- 事实依据校正结果
- 项目熟悉度观察项

输出：

- 方向有效性得分
- 推进闭环力得分
- 风险识别力得分
- 组织行为健康度得分
- 事实依据力校正分
- 项目熟悉度观察标签
- AI 替代风险指数
- 风险标签
- 行为特征摘要

### Agent 4：报告官 Report Writer

职责：

- 生成周报和专项风险提示
- 通过飞书文档或消息发送给指定角色

输入：

- 评估结果
- 风险预警
- 证据摘要
- AI 替代风险指数

输出：

- 管理者周报
- 风险提示
- 改进建议

## 6. 技术分工与人机协同

### 6.1 重新拆解后的技术分工

#### 脚本最适合做的事

- 任务触发与调度
- 会议、Base、文档数据读取
- 数据清洗与结构化
- 同项目历史会议召回
- 指标计算
- Base 写回与消息发送
- 测试数据 seed 与清空

#### 工具调用最适合做的事

- 文档切片
- 证据检索
- JSON 校验
- 报告模板渲染

#### 大模型最适合做的事

- 识别当前会议中的关键发言
- 提炼方向、闭环、风险和组织行为信号
- 判断当前结论是否被同项目历史会议和项目结果支持
- 识别证据冲突、低置信度和需要人工复核的敏感结论
- 对核心维度、事实依据校正项和 AI 替代风险指数进行归因解释
- 生成管理周报与建议

### 6.2 非线性流程与人机协同设计

为了避免系统变成固定流水线，当前方案增加三个非线性节点。

#### 1. 评估规划

系统先判断本次会议应该重点评什么，而不是每次机械跑完整链路：

- 如果本次会议没有明显方向决策，降低方向有效性的分析深度
- 如果项目延期或风险升级，增强风险识别和闭环复核
- 如果出现疑似辱骂、羞辱、严重甩锅，进入组织行为高风险流程
- 如果历史表现稳定且无异常，生成轻量周报

#### 2. 人工复核

以下场景不直接输出强结论，而是进入 Base 人工复核台：

- 证据冲突
- 置信度低
- 疑似辱骂、羞辱、严重甩锅等高风险行为
- AI 替代风险指数为高，且准备发送给上级或 HRBP

人工可以选择：

- 确认
- 驳回
- 降级
- 补充说明

#### 3. 反馈学习

报告发送后，HRBP、PMO 或上级管理者可以对结果打标：

- 准确
- 偏重
- 偏轻
- 证据不足
- 表述不适合发送

这些反馈写回 Base，用于下一轮评估规划、权重调优和提示词优化。

## 7. 中层领导评估维度设计

从 HRBP 视角看，这个项目不应该把“是否记得每个项目细节”当成主要矛盾。中层负责人往往同时覆盖多个项目，短期遗忘部分细节是正常现象，组织真正关心的是：

- 他给出的方向是否有效
- 他推动事项是否真正落地
- 他是否能识别风险并避免项目失控
- 他是否对团队造成负面管理影响

因此建议把原来的“项目理解力”从核心维度降级为观察项，把评估重心改为以下结构。

### 1. 方向有效性

定义：

- 不看中层是否记住每一个项目细节，而看他在会议中给出的判断、路径和决策方向，最终是否被项目结果验证

看点：

- 会议中提出的方向，后续是否被持续推进
- 项目结束时的最终形态，与当时提出的方向是否一致
- 被废止、推翻、回滚的方向占比有多高

建议指标：

- 方向采纳率
- 方向完成率
- 方向废止率
- 方向回滚率

证据来源：

- 会议决策点
- 后续任务流转
- 项目周报
- 阶段复盘
- 项目最终结果

### 2. 推进闭环力

定义：

- 衡量中层是否能把“会上结论”转成“会后动作”和“最终交付”

看点：

- 会后是否形成明确 owner、截止时间、下一步动作
- 是否能持续追踪未闭环事项，而不是只在会上表态
- 是否能推动跨团队依赖继续前进

建议指标：

- 行动项生成率
- 行动项闭环率
- 延期事项恢复率
- 跨团队阻塞消除率

证据来源：

- 任务表
- 风险跟进表
- 会后状态更新

### 3. 风险识别力

定义：

- 衡量中层是否能较早识别关键风险，并推动合理应对，而不是等问题爆炸后再被动响应

看点：

- 是否能主动指出真实关键风险
- 是否能区分主要风险和次要噪音
- 是否能提出可执行的缓释动作

建议指标：

- 风险提前识别率
- 高等级风险命中率
- 风险缓释动作落地率

证据来源：

- 会议中的风险提及
- 风险表变化
- 周报/复盘中的风险记录

### 4. 组织行为健康度

定义：

- 衡量中层在会议中的行为是否健康、专业、可持续，避免把“能压人、会开会”误判成“会管理”

看点：

- 是否存在明显废话过多、无效冗长、重复表态
- 是否存在公开指责、辱骂、羞辱、情绪化施压
- 是否存在打断他人、否定下属但不给方向、甩锅式表达

建议指标：

- 冗余发言占比
- 有效决策发言占比
- 负向行为触发次数
- 高风险语言事件数

证据来源：

- 会议妙记全文
- 发言轮次切分
- 语言风险标签

### 5. 事实依据力（降为低权重校正项）

定义：

- 继续保留，但不建议作为主要权重，而是作为对其他核心判断的校正项

原因：

- HR 通常不会因为中层一两次没记住文档细节就直接下负面结论
- 但如果长期“拍脑袋”“无依据判断”，仍然应当作为风险信号

看点：

- 发言是否能被任务状态、风险状态、文档、历史决策支持
- 是否经常出现无依据判断
- 是否出现与事实明显冲突的表述

建议用法：

- 低权重纳入总分
- 或作为扣分项，而不是主评分项

### 6. 项目熟悉度（降为观察项）

定义：

- 用来观察该中层对项目细节的掌握程度，但不直接作为主要淘汰依据

适合场景：

- 判断是否需要补信息同步
- 判断是否项目跨度过大、管理带宽不足

不建议：

- 因为短期记忆偏差，直接推导出“管理能力差”

### 7. 建议权重

- 方向有效性：`35%`
- 推进闭环力：`30%`
- 风险识别力：`20%`
- 组织行为健康度：`10%`
- 事实依据力：`5%`

项目熟悉度不纳入主总分，只作为观察标签单独展示。

### 8. 最终新增指标：AI 替代风险指数

这个指标不建议写成“是否会被 AI 替代”，而建议更专业地包装成：

**AI 替代风险指数 / AI Replaceability Risk**

定义：

- 衡量一个中层当前的管理工作中，有多大比例停留在“信息搬运、重复追问、无效开会、低质量表态”层面，而没有体现出人类管理者更有价值的判断、协调、承担和组织影响力

核心逻辑：

- 如果一个中层的主要行为只是转述状态、重复催办、冗长表态、低质量同步，而方向判断、风险判断、闭环推动和组织行为都较弱，那么他更容易被 AI 助手、自动化流程或更精简的组织结构替代

建议构成：

- 高冗余发言占比
- 低方向有效性
- 低闭环达成率
- 低风险识别贡献
- 高事实冲突率
- 高负向管理行为风险

输出方式建议：

- `低替代风险`
- `中替代风险`
- `高替代风险`

不要直接输出“建议裁撤”，而是输出：

- 该岗位当前的人类管理增值不足
- 建议通过辅导、流程重构、AI 工具协同或岗位重设计进行干预
- 周报/复盘中的风险记录
- 风险项后续状态变化

## 8. 最关键的“评估逻辑”

评委很可能会问一句：你凭什么评价一个中层？

所以必须把逻辑说清楚：

**我们评估的不是“人格特质”，而是“在项目协作场景中可被观察、可被追踪、可被验证的管理行为质量”。筛选特别差的，容易被ai替代的**

建议采用三层评估模型：

### 第一层：原始事实

- 会议纪要
- 任务状态变化
- 文档版本与更新时间
- 风险项变化
- 会后动作记录

### 第二层：行为指标

- 发言依据率
- 风险识别率
- 会后任务落地率
- 延期跟进及时率
- 同项目历史会议一致率

### 第三层：能力判断

- 方向有效性
- 推进闭环力
- 风险识别力
- 组织行为健康度
- 事实依据力校正项
- 项目熟悉度观察项

这样你的系统就不是“LLM 主观打分”，而是：

- 脚本先把事实组织好
- 工具先把证据召回好
- Agent 再在事实和证据之上做归因和总结

## 10. 状态流转设计

为了满足“数据产生 -> 状态更新 -> Agent 处理 -> 决策 -> 反馈 -> 再流转”，可以这样设计：

1. 新会议/新任务进入系统

- 状态：`raw`

1. 数据采集员清洗并结构化

- 状态：`normalized`

1. Evaluation Planner 生成本次评估重点、执行计划和人工复核规则

- 状态：`planned`

1. Management Reviewer 与 Risk & Behavior Auditor 分别完成管理动作 review、风险识别和组织行为审计

- 状态：`analyzed`

1. 如果存在证据冲突、低置信度或高风险行为，进入人工复核

- 状态：`pending_human_review`

1. 能力评估员整合多维结论，生成综合判断与 AI 替代风险指数

- 状态：`evaluated`

1. 报告官生成报告并发送

- 状态：`reported`

1. 后续任务继续跟踪，进入下一轮

- 状态：`tracking`

1. HRBP、PMO 或上级管理者对报告进行反馈标注

- 状态：`feedback_collected`

## 11. 一个最有说服力的业务闭环

建议你把演示聚焦在一个真实且清晰的场景：

### 场景：产品/研发项目周会中的项目型中层负责人评估

流程：

1. 项目例会结束，飞书会议纪要和妙记同步到系统
2. Data Collector 把会议纪要拆成发言事实、决策点、风险点、行动项
3. Management Reviewer 提炼该中层在会上给出的方向，并结合后续任务、复盘和同项目历史会议做 review
4. Management Reviewer 同时检查会议决策是否沉淀为 owner、DDL、后续跟进，并衡量闭环程度
5. Risk & Behavior Auditor 识别是否提前暴露关键风险、缓释动作是否有效，并审计废话密度、打断、甩锅、羞辱性表达等组织行为风险
6. Capability Assessor 汇总 4 个核心主维度 + 1 个校正项，形成综合判断与 AI 替代风险指数
7. Capability Assessor 发现两个问题：

- 对上线风险识别不足
- 会后任务闭环率低

1. Report Writer 自动输出周报：

- 本周管理表现总结
- 证据链样例
- review 复核结论
- 风险说明
- 下周改进建议

1. 报告写入 Base，并通过飞书文档/消息发送
2. 下一周继续跟踪整改是否有效

这个闭环非常适合做答辩 demo。

## 12. 给评委看的亮点设计

### 亮点 1：不是单点评价，而是持续观察

强调系统做的是“连续时间上的管理行为画像”，不是一次会议后的片面结论。

### 亮点 2：不是纯主观打分，而是证据驱动

每个结论背后都有：

- 发言摘要
- 关联任务
- 关联文档
- 风险与结果

### 亮点 3：不是只看会说，更看会不会推动

很多系统只能分析发言内容，你这个系统还能看：

- 会后有没有动作
- 动作有没有闭环
- 决策有没有带来改善

### 亮点 4：review 机制提升可信度

系统不会只根据一场会议下结论，而是会调取同项目最近 3 到 5 场会议做复核，判断结论是否稳定、是否有连续证据支持。

## 13. 风险与治理设计

这个部分一定要写进方案里，不然容易被质疑。

### 1. 避免“一票否决式打分”

系统输出应为：

- 风险提示
- 能力画像
- 改进建议

而不是直接输出“这个领导不行”。

### 2. 保留证据链

所有结论都能追溯到会议、任务、文档和状态变化。

### 3. 增加人工复核接口

高风险结论进入复核状态，由人决定是否采纳。

### 4. 只评估业务行为，不评估人格

例如：

- 可以评估“是否形成闭环”
- 不要评估“是否情商低”

## 15. 建议的 MVP 范围

为了比赛落地，建议先做一个可跑通、可演示、可复现的 MVP，不要一开始追求过全。

### MVP 只做 3 类数据

- 会议纪要/妙记
- Base 项目、任务、风险数据
- 项目主文档、周报、复盘

### MVP 只做 1 类对象

- 产品/研发类项目的中层负责人

### MVP 只做 1 类 review

- 同项目最近 3 到 5 场会议复核

### MVP 只做 4 个核心主维度 + 1 个校正项

- 方向有效性
- 推进闭环力
- 风险识别力
- 组织行为健康度
- 事实依据力（低权重校正项）

### MVP 只输出 2 类结果

- 周报
- 风险预警

这样最容易做出稳定 demo。

## 16. 推荐你在答辩时的表述方式

你可以这样讲：

“我们做的不是一个简单的领导评分机器人，而是一个基于飞书协作数据持续运行的管理效能洞察系统。当前版本聚焦产品和研发项目周会中的项目型中层负责人，通过飞书 OpenAPI 拉取会议纪要、Base 中的项目任务风险数据，以及项目主文档、周报、复盘，对中层在本次会议中的表现做出初判，再调取同项目最近 3 到 5 场会议进行 review 复核，最终输出可追踪、可解释的管理洞察和改进建议。”

这句话会比“我做一个评估领导的机器人”高级很多，也更稳。

## 17. 最终建议

如果你要在比赛里赢，最推荐的版本不是：

**只分析会议发言**

而是：

**方向有效性判断 + 同项目历史会议 review + 任务闭环跟踪 + 风险与组织行为审计 + 管理效能报告**

一句话总结你的最佳切入点：

**做一个围绕产品/研发项目中层负责人的“管理效能洞察 Agent 组织”，让飞书里的协作数据自己说话。**
