# 支付链路升级项目主文档

本文档为支付链路升级项目的主控文档，面向支付中台、商户接入、测试、运维与业务管理层共同维护。文档目标是统一项目背景、业务目标、技术范围、关键里程碑、验收口径、风险清单和对外沟通节奏，避免不同团队对“主链路稳定”“可灰度”“可回滚”出现口径偏差。

## 一、项目背景

过去两个季度，支付主链路在高峰时段暴露出两个持续性问题：第一，路由切换时延波动偏大，导致少量交易在流量峰值时段出现体验抖动；第二，退款状态回写在跨服务重试场景下存在一致性缺口，补单和人工干预比例上升。三月大促期间，整体支付成功率没有跌破红线，但退款回查、补单、商户工单显著增加，商户运营团队对支付链路稳定性与回滚可控性提出了更明确要求。

本次项目并不是简单替换一段支付路由逻辑，而是一次围绕“支付主流程、退款回调、配置同步、回滚能力”的联合收口。业务方希望五月第一周提交灰度申请，五月中旬完成首批商户切换。因此，本阶段的核心任务不是把某一条技术链路跑通，而是让“是否可以灰度”具备充分、可追溯、可复核的证据链。

## 二、业务目标

### 2.1 北极星指标

- 支付成功率 >= 99.95%
- 退款状态回写一致性 >= 99.90%
- 商户配置回滚执行时间 <= 10 分钟
- 灰度首周 P1 事故数 = 0

### 2.2 项目目标

- 完成新支付路由切换，并保持主链路稳定性
- 将退款回调链路纳入统一收口和验证口径
- 在灰度前完成回滚方案验证，避免商户配置脚本成为单点风险
- 形成上线前置条件清单，让支付、测试、运维、商户接入在同一口径下判断是否可灰度
- 让管理层在周会中不再用“进度接近完成”代替“风险已闭环”

### 2.3 本阶段成功定义

本阶段不以“代码提交完成”作为成功标志，而以下列四项共同满足为准：

1. 主支付链路稳定性验证通过
2. 退款回调链路阻塞项清零，并产出验证记录
3. 异常退款、弱网、并发补单等关键样本验证齐备
4. 回滚方案完成演练，并有运维和商户接入共同确认

## 七、技术方案摘要

### 7.1 主支付链路

- 引入新路由编排逻辑
- 保留旧路由作为 fallback
- 通过按商户、按渠道、按地域三个维度控制切流

### 7.2 退款回调链路

- 统一退款回调入口
- 增加跨服务重试幂等校验
- 增强补单状态回写一致性检查

### 7.3 配置与回滚

- 商户配置变更与灰度开关绑定
- 单商户与批量商户分别提供回滚脚本
- 运维侧需保留回滚执行窗口和操作记录

### 7.4 监控与告警

- 支付成功率
- 退款回调成功率
- 配置同步成功率
- 回滚执行时延
- 工单与告警联动趋势

## 八、上线前置条件

### 8.1 硬前置条件

- 退款回调链路 2 个阻塞问题关闭
- 异常退款与弱网样本覆盖补齐

- 晚间回归窗口确认且回归结果出齐

### 8.2 软前置条件

- 商户侧监控话术与升级路径已同步
- 灰度观察群值班表已确认
- 当日回滚演练记录已归档到项目文档

## 九、验收口径

### 9.1 功能验收

- 正常支付成功
- 异常退款可追踪
- 弱网重试下幂等校验稳定
- 并发补单不会造成状态错乱

### 9.2 质量验收

- 支付成功率达到目标线
- 退款一致性达到目标线
- 配置同步失败重试机制有效
- 回滚可在规定时间内完成

### 9.3 发布验收

- 灰度前置条件清单完成
- 演练记录可回溯
- 风险 owner 明确
- 观察指标、值班人、升级路径明晰

## 十五、当前判断

当前阶段最大的误区，是把“主支付链路已稳定”误解成“已经可以申请灰度”。从项目治理口径看，只有当退款回调、样本覆盖、回滚演练三件事全部收口，并形成可回溯记录，灰度申请才具备说服力。任何一个点没有闭环，后面一旦出问题，影响的不只是一次发布，而是支付链路的可信度、商户侧信任和团队后续上线节奏。
